# Running daily: hooks and schedulers

Two layers. Use either or both (default: both).

1. **Scheduler**: something starts a run at a set time, even if you never open a session.
2. **Catch-up hook**: when you open a session, `scripts/catch_up.py` checks `uptodate/runs.log`; if today has no run it adds one line to the agent's context asking it to offer the run. Silent if today already ran or if it already reminded you today.

Both are idempotent: a day that already has an all-topics run (`scope=all`) in `runs.log` is not run again.

**Quiet days cost nothing.** `scripts/precheck.py` (used by `run-daily.sh` and `run-daily.ps1`) works out which topics are due and fingerprints their sources with plain HTTP. If nothing is due or changed, it writes the quiet-day digest itself and the agent is never started. Use the same pattern with any scheduler: run `precheck.py` first and start the agent only on exit code 10. Exit code 11 means no due topic could be checked because none of their sources could be fetched: it writes a "Could not check" section and leaves the day open, so the next run or the catch-up hook tries again. If only some topics could not be checked, the exit code is 0 and the digest lists them; they stay due. Any other exit code (not 0, 2, 10 or 11) means precheck itself failed: treat it as an error, never as a quiet day.

In every template replace `/path/to/skills/what-changed` with where you installed the skill and `/path/to/uptodate` with your store.

## Schedulers

- **cron / launchd (macOS, Linux)**: `scheduler-cron/run-daily.sh` (set `WHAT_CHANGED_HOST` and `WHAT_CHANGED_PROJECT`; for the claude host, optionally `WHAT_CHANGED_FETCH_DOMAINS`, a comma-separated list of extra hosts the agent may fetch besides those in `topics.yaml`, `*.example.com` for subdomains, `*` for any host). With the claude host it needs Claude Code 2.1.248 or later (`--restricted`); it checks the version before every run (with `scripts/cli_version.py`, which gives `claude --version` 30 seconds, or `WHAT_CHANGED_VERSION_TIMEOUT`) and stops with a message if `claude` is missing, older or does not answer. It runs `~/.local/bin/claude` (where Claude Code's installer puts it) if that exists, else the first `claude` on `PATH`; to use another one, set `WHAT_CHANGED_CLAUDE` to its full path (`command -v claude` prints it). It also sets `USER` if cron or launchd did not, because `claude` needs it to find its login. It runs the skill's scripts with the first Python 3.11 or later it finds (`python3`, then `python3.15` … `python3.11`, `~/.local/bin/python3`, Homebrew, python.org); set `WHAT_CHANGED_PYTHON` to choose one. cron starts with a minimal PATH, so set the rest: `0 7 * * * PATH=/usr/local/bin:/opt/homebrew/bin:/usr/bin:/bin WHAT_CHANGED_PROJECT=$HOME/notes WHAT_CHANGED_HOST=claude /path/to/skills/what-changed/adapters/scheduler-cron/run-daily.sh`. On macOS prefer launchd: `scheduler-cron/com.example.what-changed.plist` runs once after wake if the machine slept through 07:00. Output goes to `~/.local/state/what-changed/<id>/` (`$XDG_STATE_HOME` if set), outside the project, so an agent cannot plant a symlink there. When a run cannot finish, the reason goes to `<id>/<date>-error.txt` there, and the catch-up hook passes it on in your next session. It reads `topics.yaml` only through a copy you approved, kept there too: a run stops while `topics.yaml` differs from it, and the message gives the command that approves that version (`WHAT_CHANGED_APPROVE_TOPICS=<32 characters> … run-daily.sh`, an approve-only step) and the file that lists the added and removed sources (`<id>/<date>-topics.diff`). Its first run for a project approves `topics.yaml` as it is (every approval is also listed in `<id>.approvals.log`); once it has run there, a missing copy (the first run after updating from a version before 0.1.6) stops once. On a day that already ran, a plain run says whether the next run would stop, with the command. Only one run goes at a time (a second start exits), and `precheck.py` is stopped after 15 minutes if it has not finished.
- **Task Scheduler (Windows)**: `scheduler-windows/run-daily.ps1`, claude host only. **Not tested yet.** It takes `-Project`, and optionally `-FetchDomains`, `-Claude` and `-Python` (or the same `WHAT_CHANGED_*` environment variables). The agent gets no shell; the script runs `precheck.py` and `fingerprint.py` before it (the fingerprints go into the prompt) and `log_run.py`, `check_ledger.py` and `verify_quotes.py` after it. Like `run-daily.sh`, it stops while `topics.yaml` differs from the copy you approved; approve the reviewed version with `-ApproveTopics <32 characters>`. The message gives the command, run through `powershell -NoProfile -ExecutionPolicy Bypass -File` like the task; it is in `%USERPROFILE%\.local\state\what-changed\<id>\<date>-error.txt` (the catch-up hook passes it on), and the added and removed sources are in `<date>-topics.diff` next to it. To register a daily task that also runs after a missed start (machine asleep or off), in PowerShell:
  ```powershell
  $a = New-ScheduledTaskAction -Execute 'powershell.exe' -Argument '-NoProfile -ExecutionPolicy Bypass -File "C:\path\to\what-changed\adapters\scheduler-windows\run-daily.ps1" -Project "C:\path\to\project"'
  Register-ScheduledTask -TaskName 'what-changed' -Action $a -Trigger (New-ScheduledTaskTrigger -Daily -At 7am) -Settings (New-ScheduledTaskSettingsSet -StartWhenAvailable)
  ```
- **GitHub Actions**: `scheduler-github-actions/what-changed.yml`. Runs in the cloud, commits `uptodate/` back, so git history is your knowledge history. Needs an `ANTHROPIC_API_KEY` (or `CLAUDE_CODE_OAUTH_TOKEN`) repository secret, which you add yourself; extra hosts to fetch go in a `WHAT_CHANGED_FETCH_DOMAINS` repository variable.
- **Host apps with built-in scheduling** (Claude Desktop routines, ChatGPT scheduled tasks, …): create a daily task whose prompt is `Use the what-changed skill: run all due topics in light mode. Store: <path>.`

## Why not only an instructions file (CLAUDE.md / AGENTS.md / GEMINI.md)?
An instructions file does not start a session, and the model may not follow it. Use it as the fallback for hosts without a session-start hook, not as the scheduler.
